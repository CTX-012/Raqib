raqib documentation

One screen for every workload competing for your GPU — and a governor that can evict the one starving the rest.

raqib watches every process fighting over your GPU — ROS 2 nodes, LLM servers (ollama, vLLM, llama.cpp), agents, embeddings — in a single terminal UI and a web dashboard. Unlike read-only tools, it can also act: an opt-in governor that terminates a workload starving the others.

This site is the complete guide. New here? Start with Installation → First run. Looking for something specific? Jump to Configuration, the governor, or the REST API.

🖥️ One pane of glass

Every GPU/VRAM/CPU/thermal workload in one view — stop juggling nvtop + btop + ollama ps.

🎯 Honest metrics

Unmeasurable VRAM shows “—”, never a fake 0. A blank means “unknown,” not “idle.”

📊 Live LLM health

Reachability + tokens/sec for ollama, vLLM, and llama.cpp, scraped live.

🛡️ The governor

Can kill a runaway workload — off by default, opt-in, and verifiable before you arm it.

Installation

Linux only. raqib reads /proc, GPU NVML, thermal sysfs, and (optionally) the ROS 2 graph. NVIDIA GPUs get full VRAM/thermal/power metrics; other setups still get process, CPU, and memory monitoring. Tested on Ubuntu 22.04 / 24.04.

First run

raqib init      # writes a commented, safe-by-default config to ~/.config/raqib/raqib.toml
raqib           # starts: TUI + web dashboard on http://localhost:7070

raqib init writes a config with monitoring on and the governor off. It's heavily commented — read it before changing anything.

Config discovery order

raqib looks for its config in this order:

  1. --config <path> (explicit)
  2. ./raqib.toml
  3. ~/.config/raqib/raqib.toml ← where raqib init writes
  4. /etc/raqib/raqib.toml

Configuration

raqib init writes a fully-commented file. Here's every section:

[web]
# The web dashboard needs an explicit auth choice — pick ONE:
allow_no_auth = true         # OK on localhost / trusted LAN, no token needed
# auth_token = "your-secret" # required for exposed/untrusted networks
                             # clients send: Authorization: Bearer <token>

[governor]
# auto_actuate = true is THE ARM. Off by default.
auto_actuate         = false
kill_sustain_secs    = 30    # a breach must persist this long before a kill fires
rate_limit_max_kills = 3     # max kills per 60s window
sigterm_grace_secs   = 5     # SIGTERM → wait → SIGKILL grace period

[policy]
default_ai_action = "Allow"  # "Allow" = nothing killable by default
                             # "Kill"  = AI/robotics workloads killable when armed
blocklist = []               # comms that ARE killable  (matched vs /proc/<pid>/comm)
allowlist = ["ruby", "rviz2", "ros2", "claude", "sshd", "bash", "systemd"]
                             # comms that are NEVER killed

[thresholds]
vram_attention_pct = 85.0    # attention level (must be ≤ critical)
vram_critical_pct  = 95.0    # breach level — feeds the governor
ram_attention_pct  = 85.0
ram_critical_pct   = 95.0
thermal_amber_c    = 80.0
thermal_red_c      = 90.0    # thermal breach can make MANY processes eligible at once
⚠️ The “ruby” gotcha. The allowlist/blocklist match /proc/<pid>/comm, not raqib's display name. Gazebo runs as ruby (it's Ruby-launched) — so to protect Gazebo, allowlist ruby, not Gazebo. rviz2's comm matches its name, so rviz2 works directly. Rule of thumb: allowlist the name you'd see in ps -o comm=, not the friendly name raqib shows.

The governor

raqib can kill processes. This is its most powerful feature and the one to understand clearly.

Out of the box, raqib kills nothing. It observes. The governor stays disabled until you make two deliberate choices:

[governor]
auto_actuate = true            # (1) allow the governor to actually act

[policy]
default_ai_action = "Kill"     # (2) make workloads eligible to be killed

Both. On purpose. And the web API cannot arm the governor — that's config-only, by design, so nothing remote can turn on the killer.

The two kill paths

PathRequires arming?How
Manual killNoSelect a workload in the TUI → confirm the kill_confirm card → raqib sends SIGTERM. The primary kill path.
Automatic killYesWhen armed, the governor terminates a workload that breaches a threshold and stays over it for kill_sustain_secs.

Before you arm it

  1. Verify the policy first with raqib config check — it prints the exact allowlist/blocklist and shows KILLER IS ARMED / DISARMED. Confirm your real workloads are protected before the killer goes live.
  2. Set an allowlist naming every workload you never want touched (using comms — see the ruby gotcha). The default protects only system processes.
  3. Give thermal_red_c real headroom above your normal temperature — a thermal breach can make many processes eligible at once.
  4. Start conservative — low rate_limit_max_kills, generous kill_sustain_secs, so you can watch it behave before trusting it.
Current kill-selection is conservative-but-simple (a fixed rule, not “the biggest offender”). Smarter selection is on the roadmap. The safe posture: observe by default; arm only with an allowlist in place and verified via config check.

raqib config check

The nginx -t of raqib: validate your config and print the exact policy that will load — thresholds, and the full allowlist and blocklist. Check what the tool will do before it does it. Essential before arming.

$ raqib config check
raqib config check — /home/you/.config/raqib/raqib.toml  (discovered)
────────────────────────────────────────────────────────────────
[governor]
  auto_actuate      = false      ← KILLER IS DISARMED
  kill_sustain_secs = 30
[policy]
  default_ai_action     = "Allow"
  allowlist (…): bash, claude, ros2, ruby, rviz2, sshd, systemd, …
  blocklist (…): (none)
[thresholds]
  vram_critical_pct = 95.0   thermal_red_c = 90.0   …
VALIDATION: OK

Exit codes: 0 valid, 1 no config found, 2 found but invalid — so it scripts cleanly as a pre-flight check. Point it at any file with --path.

Hands-on: see an LLM appear with live throughput

# start raqib headless
nohup raqib --no-ui --bind 127.0.0.1 --port 7070 > /tmp/raqib.log 2>&1 & disown

# start an ollama model (or vLLM / llama-server)
ollama run llama3.2

# ask raqib what it sees:
curl -s localhost:7070/api/snapshot \
  | jq -r '(.workloads // .processes)[] | "\(.name) [\(.category)] tok/s=\(.tokens_per_sec)"'

The server shows up detected, classified as an LLM workload, reachable. Generate a few tokens and tokens_per_sec fills in.

llama.cpp: start llama-server with --metrics (or LLAMA_ARG_ENDPOINT_METRICS=1) so its Prometheus endpoint is enabled — otherwise raqib detects the server but throughput stays blank.

Hands-on: the snapshot API

raqib's web layer is a small REST API — easy to script against:

curl -s localhost:7070/api/snapshot | jq .     # full system snapshot
curl -s localhost:7070/api/settings | jq .     # resolved thresholds + governor state
curl -s localhost:7070/api/health              # liveness

# top 5 VRAM consumers right now:
curl -s localhost:7070/api/snapshot \
  | jq -r '.top_processes.by_vram[] | "\(.vram_mb)MB  \(.name)"' | head -5

Hands-on: safe kill demo

Demonstrates the governor's kill path on a throwaway canary, with your real work protected. Read every step — this arms the governor.

# 1. write a test config: ONLY a "ram_canary" is killable, everything else protected
mkdir -p ~/.config/raqib
cat > /tmp/raqib-killdemo.toml <<'TOML'
[web]
allow_no_auth = true
[governor]
auto_actuate = false          # still OFF — we verify first
kill_sustain_secs = 10
[policy]
default_ai_action = "Allow"   # nothing killable by default
blocklist = ["ram_canary"]    # ONLY the canary is killable
allowlist = ["bash","zsh","sh","systemd","init","sshd","ros2","ruby","rviz2","claude"]
[thresholds]
ram_attention_pct = 40.0
ram_critical_pct  = 50.0
thermal_red_c     = 120.0     # thermal fenced out of this demo
vram_critical_pct = 95.0
TOML

# 2. VERIFY before arming — confirm blocklist=[ram_canary], real work on allowlist:
raqib config check --path /tmp/raqib-killdemo.toml

# 3. launch a disposable RAM hog named "ram_canary":
cp /usr/bin/python3 /tmp/ram_canary
/tmp/ram_canary -c "x=bytearray(6*1024*1024*1024); import time; time.sleep(600)" &

# 4. ARM: set auto_actuate=true in the file, re-verify, then run:
raqib config check --path /tmp/raqib-killdemo.toml   # must show KILLER IS ARMED
nohup raqib --no-ui --config /tmp/raqib-killdemo.toml --port 7071 >/tmp/kd.log 2>&1 & disown

# 5. watch: the canary is killed; your shells / ROS / agents survive:
watch -n2 'pgrep -a ram_canary || echo "canary killed"; pgrep -x bash >/dev/null && echo bash-alive'

# 6. DISARM when done:
pkill -INT raqib; rm -f /tmp/ram_canary

The point: raqib kills the thing you told it to, and nothing else. config check (steps 2 & 4) is what lets you prove that before the killer runs.

REST API

Served on the web port (default 7070). Unauthenticated on localhost by default; requires Authorization: Bearer <token> if auth_token is set.

EndpointReturns
GET /api/healthliveness
GET /api/snapshotfull system snapshot — workloads, vitals, top processes, alerts
GET /api/streamWebSocket — same shape as snapshot, pushed live
GET /api/settingsresolved thresholds, governor state, config path
GET /api/historyrecorded event log

Key snapshot fields per workload: name, category, cpu_pct, rss_mb, vram_mb (null if unattributable), tokens_per_sec, kv_cache_peak_pct, probe_status, status.

Troubleshooting

raqib gets “Stopped” / suspended when I background it

The TUI grabs the terminal. Use --no-ui for background/service runs: nohup raqib --no-ui … & disown.

An LLM server is detected but tokens/sec is blank

For llama.cpp, start llama-server with --metrics (Prometheus endpoint is off by default). For any server, throughput only populates during / just after generation — an idle server reads blank.

My workload isn't protected even though I allowlisted it

The allowlist matches /proc/<pid>/comm, not the display name. Check the real name with ps -o comm= -p <pid> (e.g. Gazebo is ruby) and allowlist that.

All my workloads show “—” for VRAM

If your GPU processes run in containers, the host driver often can't attribute per-process VRAM. raqib honestly reports “—” rather than a fake 0. Device-total VRAM still works.

I rebuilt but I'm still seeing old behavior

Restart the running raqib — you're likely still on the old binary. pkill raqib then relaunch. raqib --version confirms which build is running.

config check is valid but the running instance ignores it

Confirm the running instance loaded that file: curl -s localhost:7070/api/settings | jq .config_path. If it points elsewhere (or you edited the file), restart raqib.

FAQ

Is it safe to run on my production box?

Monitoring is passive and read-only. The governor is off by default and can't be armed remotely. As long as you don't set auto_actuate = true, raqib will never kill anything on its own — and even the manual kill requires an explicit TUI confirmation.

Does it work without an NVIDIA GPU?

Yes — you lose the NVML VRAM/thermal/power metrics, but process, CPU, and memory monitoring still work. AMD/Intel metrics beyond the basics are on the roadmap.

What's “rcl link” detection?

ROS 2 nodes link the rcl (ROS client library). raqib checks a process's loaded libraries to identify genuine ROS 2 graph participants, rather than guessing from names.

Why does it say “edge_monitor” anywhere?

raqib was previously named edge_monitor. Some internal identifiers (the library crate, the Prometheus metric prefix edge_monitor_*) keep the old name for compatibility; the binary, config, and everything user-facing are raqib.
