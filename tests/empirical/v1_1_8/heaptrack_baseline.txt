CRITICAL VISIBILITY ISSUE: v1.1.7 ships with mimalloc as
`#[global_allocator]`. mimalloc allocates pages via mmap()
DIRECTLY, bypassing libc malloc/free. heaptrack's LD_PRELOAD
hook intercepts libc malloc only — so the 1.78 GB of mimalloc-
managed RSS is INVISIBLE to heaptrack. The 610K libc-malloc
calls are the residual non-mimalloc allocations (clap argument
parsing, std::process pipes, etc.). The ~72 KB "leaked" is
genuinely libc-side leaks; mimalloc's growth is unmeasurable
through this tool with the v1.1.7 binary as-shipped.

This invalidates the dispatch's PHASE 0 "leak-bytes top-N"
decision gate as written. Switched to /proc-based diagnostic
(Part B) which observes the kernel-side resource accumulation
directly, independent of which allocator is in use.

DECISION GATE — REVISED
────────────────────────────────────────────────────────────

Inspector's DISPATCH 24 prediction (candidate 4): tokio
`Child` handle leak because `kill()` does not `wait()`.
Inspector's note: "tokio's documented best-effort reaper
(tokio-rs/tokio#2685)" — without explicit wait(), the per-Child
signal/pidfd registration and the eventfd backing it never
release.

Observed: 226 eventfd FDs at t=185s, growing ~1/s.
            10 ROS2 publishers × 1 B3 echo probe/PID/tick × 1 tick/s
            = 10 spawn-kill cycles/s; eventfd growth at ~1/s is
            consistent (cycle batching/coalescing in tokio).
Observed: 0 zombie processes — tokio's reaper IS removing the
            process from the process table, but the tokio-side
            Child handle state (signal registration / pidfd /
            eventfd) is NOT being released without an explicit
            wait().

Verdict: candidate (4) CONFIRMED via FD accumulation pattern.
The dispatch's specified fix — `child.wait()` after `child.kill()`
with a 500ms guard — directly addresses this by giving tokio's
Drop-on-completion the chance to release the per-Child state.

Sysinfo wasted-work finding (DISPATCH 24 candidate 2):
NOT directly diagnosed here (allocator-blind), but Inspector's
~1000× alloc-reduction analysis is a separate per-tick churn
reduction that lands as ITEM 2 alongside ITEM 1.

Verdict: proceed with both ITEMs as specified.

────────────────────────────────────────────────────────────
heaptrack vs /proc — methodological note
────────────────────────────────────────────────────────────

For future leak-diagnosis dispatches on this binary, heaptrack
must either:
  - Be paired with a fresh build that disables mimalloc
    (`#[cfg(feature = "diag-glibc-alloc")]`-style toggle), OR
  - Be replaced with `pmap` / `smaps_rollup` / `/proc/$PID/fd`
    snapshotting which sees kernel-side resources independent
    of allocator.

The DISPATCH 22 PHASE 0 profile worked because v1.1.6 had no
mimalloc — heaptrack hooked the only allocator. v1.1.8+ requires
the methodological shift above.
