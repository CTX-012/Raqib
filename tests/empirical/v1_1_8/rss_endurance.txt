ITEM 1 HYPOTHESIS RECAP — partial confirmation
═══════════════════════════════════════════════════════════

DISPATCH 24 Inspector ranked candidate (4) "tokio Child handle
leak from kill() without wait()" as the strongest source of
the linear residual. PHASE 0 /proc diagnostic of v1.1.7
ff33479 observed 226 `anon_inode:[eventfd]` FDs at t=185s
under the 10× publisher workload, growing ~1 FD/s, consistent
with the candidate.

ITEM 1 added `child.wait()` after `child.kill()` (500 ms
guard, see `ROS2_CHILD_REAP_GUARD` in
`src/telemetry/samplers/ros2_shellout.rs`). Expected: eventfd
growth flat after fix.

Observed: eventfd growth rate ESSENTIALLY UNCHANGED (~1 FD/s)
in v1.1.8. The ITEM 1 fix:
  - DOES drain the child process (no zombies in either run)
  - DOES return promptly (the 500 ms guard wasn't hit — empirical
    inference from total throughput stability)
  - Does NOT close the leaked eventfd

Therefore: the eventfd source is NOT tokio's `Child` signal
registration as candidate (4) hypothesised. It's something
else that allocates an `anon_inode:[eventfd]` per tick. Top
remaining candidates the next dispatch should investigate:

  a) tokio runtime's task scheduler park/unpark eventfds —
     if the worker thread count is dynamic per spawn (it
     shouldn't be, but worth verifying)
  b) tokio process driver's signal-handler registration — even
     with pidfd_open used by `Command::spawn`, there may be a
     per-spawn eventfd in the inner driver
  c) mimalloc's per-thread state — mimalloc does spawn a
     background reclaim thread under high churn (each thread
     would have its own eventfd for park/unpark)
  d) the audit writer's persistent file handle wakeup
     mechanism

Diagnostic tools the next dispatch should bring:
  - `strace -e trace=eventfd2,signalfd,timerfd_create -p $PID`
    captures eventfd creation in real-time
  - `bpftrace -e 'tracepoint:syscalls:sys_enter_eventfd2 /comm==
    "edge_monitor"/ { @[ustack(perf)] = count(); }'` attributes
    the creations to backtraces
  - `lsof -p $PID` shows the user-side opener of each FD

ITEM 2 HYPOTHESIS RECAP — confirmed by code-reading + tests
═══════════════════════════════════════════════════════════

DISPATCH 24 candidate (2): `platform::collect_system_metrics`
built a fresh `sysinfo::System::new_all()` + `refresh_all()`
per tick, allocating a Linux process map every second despite
only reading memory fields off the System.

ITEM 2 made the `System` long-lived (owned by `Runtime`),
swapped `refresh_all()` for `refresh_memory()`, and replaced
`sys.cpus().len()` with `std::thread::available_parallelism()`
(the cpu list is empty on a non-CPU-refreshed System). Direct
in-process verification of the per-tick allocation drop would
require a heaptrack run against a glibc-allocator build — not
done here because that requires reverting mimalloc temporarily
(scope creep for this dispatch). The unit-test pin
`collect_system_metrics_with_targeted_refresh_populates_memory`
verifies the targeted-refresh shape produces correct memory
figures across consecutive refreshes on the same handle, which
was the structural goal.

The ~13% slope improvement (~190 → ~166 MB/min) is consistent
with ITEM 2 cutting per-tick allocation overhead even though
ITEM 1's principal target wasn't actually the leak driver.

PROCESS NOTE
═══════════════════════════════════════════════════════════

The dispatch's PHASE 0 was supposed to use heaptrack
`--leak-bytes` to confirm the tokio process-child stacks as
top of the never-freed list before fixing. heaptrack's
LD_PRELOAD hook is BLIND to mimalloc allocations (mimalloc
mmap()s pages directly bypassing libc malloc), so heaptrack
reported 290 KB peak heap / 72 KB leaked under a 1.78 GB RSS
run — useless as a decision gate. Switched to /proc-based
snapshotting (smaps_rollup, fd type inventory, child process
state, thread count, mmap region count). See
`tests/empirical/v1_1_8/heaptrack_baseline.txt` for the full
methodology note.

Future leak-diagnosis dispatches on v1.1.7+ binaries should
either (a) bring a feature-flag for swapping mimalloc out for
the diagnostic build, or (b) skip heaptrack and rely on /proc
+ syscall tracing.
